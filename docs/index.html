When a dependency breaks your code, Patchery fixes it and proves the fix.

A major version lands, your test suite goes red, and someone loses an afternoon to it. Patchery reproduces the break, works the fix, and re-runs your tests — then opens a pull request only if it can show the evidence.

How it works

Three steps, and the third one is the product.

  1. 01

    Reproduce

    It pins your repository, applies the upgrade, and runs your test suite. If the failure is not real and repeatable, it stops here — there is nothing to fix.

  2. 02

    Fix

    An agent reads the failure and the changelog, and migrates the call sites. It works inside your checkout, with your tests as the only judge of whether it is done.

  3. 03

    Prove

    The patch ships with its evidence: the failing run before, the passing run after, the files it touched, and a read-only second agent's review — attached whether it agrees or not. If your tests do not pass, nothing is delivered.

The gate

Writing the fix is the easy part.

Any capable model can produce a patch that looks right. The question is what happens when it is wrong — and the answer most tools give is: it opens the pull request anyway. Patchery ends a run in one of six states, and it would rather end in the second one than guess.

  • FIXED

    The break is gone, your tests pass, and the evidence is attached.

  • REFUSED

    It found something it could not prove, so it sent nothing and said which check stopped it.

  • NO-CHANGE

    It finished its turn and had nothing worth sending.

  • EXHAUSTED

    The turn budget ran out mid-investigation. It counts against the score: a run that does not finish has not helped anyone.

  • WRONG

    It sent a patch that does not hold up. This is the number that has to stay honest.

  • BLOCKED

    The run could not get far enough to be measured — a build, a container, an environment.

REFUSED and WRONG are not the same column.

An agent that declines to send what it cannot prove is doing the job. An agent that sends it anyway is the risk you were trying to remove. A report that merges the two is measuring some other product.

It cannot shrink the test that judges it.

Tests are counted while the code is still whole — before anything is broken, so nothing the agent does afterwards can move that baseline. They are counted again after its turn. If fewer tests pass than at the start, the run is recorded WRONG, however green it looks.

Where it runs

Your code never leaves your machines.

Patchery is not a service you send a repository to. It is a file in your project that runs on your own runners, with your own key, against your own checkout. There is no Patchery server for your source to travel to, because there is no Patchery server.

Install

One file, and nothing runs until you say so.

  1. Add your model key to the repository's secrets as ANTHROPIC_AUTH_TOKEN.
  2. Save this file as .github/workflows/patchery.yml.
  3. Start it from the Actions tab, and choose which package it works on.

No scheduler and no background scanning: it runs when you dispatch it. Scheduled runs are the next thing on the list.

Full setup guide→

.github/workflows/patchery.yml 
name: Patchery

on:
  workflow_dispatch:
    inputs:
      package:      { required: true }
      target-dir:   { default: "." }
      test-command: { default: "npm test" }

permissions:
  contents: write
  pull-requests: write

jobs:
  fix:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - run: npm ci
        working-directory: ${{ inputs.target-dir }}

      - id: patchery
        uses: patchery-dev/Patchery@v0
        with:
          package:              ${{ inputs.package }}
          target-dir:           ${{ inputs.target-dir }}
          test-command:         ${{ inputs.test-command }}
          anthropic-auth-token: ${{ secrets.ANTHROPIC_AUTH_TOKEN }}

      - if: steps.patchery.outputs.changed == 'true'
        uses: peter-evans/create-pull-request@v7
        with:
          branch:    patchery/${{ inputs.package }}
          body-path: ${{ steps.patchery.outputs.pr-body-file }}
          add-paths: ${{ steps.patchery.outputs.files }}
Where it stands

Early, and specific about it.

True today

  • It fixes JavaScript and TypeScript projects with a test command.
  • It has opened a real pull request, with the evidence attached.
  • A second agent reviews every patch without write access.
  • The code is open, and the checks are in the repository, not in a brochure.

Not yet

  • No scheduled runs — you dispatch it by hand.
  • One ecosystem. Other languages are unproven, not supported.
  • No benchmark ratio to quote until the current run finishes.
  • No users to point at. There is nothing to sign up for.
